# 驗收與維運

## 正式開放前

確認校方同意收受授權及個資蒐集、正式聯絡窗口、處理地區及受託者，核定條款。預設 inactive 的條款及 `COLLECTION_ENABLED=false` 保持關閉，不能因單純展示就接收個資。

### 必須實測的整合案例

1. 匿名瀏覽說帖；匿名 POST RPC、Storage 上傳／下載、讀 submissions 均應拒絕或回空，不得取到其他資料。
2. 帳號 A 用 Email OTP 登入，錯誤及過期 OTP 不應成功；帳號 B 無法讀 A 的 submission 或 storage path。
3. A 提交文字及錄音各一件；伺服器時間、已驗證 Email、檔案大小、條款快照、簽署姓名正確，狀態 pending，不在 training_candidates。
4. 空檔、超過 50 MB、錯誤副檔名、類別不符、缺欄、不同簽署姓名、不勾選同意、非本人路徑、未上傳物件、過期條款均失敗；不要只測前端，要直接呼叫 RPC。
5. A/B 不得 UPDATE 或 DELETE submission；A 也不得 overwrite 已簽署檔案。確認匿名無法下載私人 bucket。
6. 同一 submission_id 重試只保留一筆，斷網後重新驗證可從歷史找回收據。上傳成功但 RPC 失敗時清理未簽署檔；結果不明不應刪除可能已簽署的檔。
7. 研究團隊核准資料後，僅狀態 approved 且未到期、未撤回者出現在 training_candidates；申請撤回即退出。普通帳號不能自行改為 approved。
8. 下載 JSON 收據並列印 PDF，核對版本全文、檔名、摘要、簽署人、日期；手機和鍵盤均可操作。
9. 更新條款版本後，舊頁面提交應被伺服器拒絕，不能誤簽新條款；已簽的 snapshot 不隨更新變動。
10. SMTP 實際投遞、速率限制、儲存預算與告警、備份還原皆須驗證。

## 人工審核

由 Supabase Dashboard 授權管理者查看 pending 紀錄。不要以公開連結傳閱作品。先在隔離環境掃毒、確認檔案格式與錄音內容，重新計算 SHA-256 比對 client_sha256，再查核作者、出版社、第三方內容、錄音說話者與代表權、個資及必要同意。

確認後由管理者以 transaction 更新狀態並寫入 audit_events。請替換真實 UUID，不要直接照貼 placeholder。

```sql
begin;
update public.submissions set status='approved'
where id='實際投稿UUID' and status='pending' and withdrawal_requested_at is null;
-- 下方審核紀錄僅在上方確實核准且查核完成後建立
insert into public.audit_events(submission_id,event)
select id,'approved_after_rights_and_file_review'
from public.submissions where id='實際投稿UUID' and status='approved';
commit;
```

僅 `training_candidates` 是可選清單，使用前仍須確認訓練目的符合授權。資料的入庫、去識別、分割、標註與每次訓練都記錄投稿 ID，才能追蹤撤回影響。不得把原始檔、完整語料或權重放到公開 GitHub。

## 撤回、到期與刪除

每日檢查 withdrawal_requested 與到期紀錄。收到撤回即停止新增使用，30 日內回覆並移除工作資料及衍生資料集；透過 **Storage API/Dashboard** 刪除實體物件，不能只刪 storage.objects 資料列。備份最遲 90 日輪替，隔離期間不使用。處理完成設為 withdrawn，寫稽核事件。授權證據依法及條款保留，必要時移除不必要的個資；已完成模型訓練不能承諾完全回溯移除，須評估原文輸出等補救。

每週清理超過 24 小時且沒有 submissions 引用的未簽署 Storage 物件，避免中途關閉造成暫存堆積。刪除前再查一次引用，不要清掉已簽署檔案。設定儲存預算告警與 Auth 速率限制；大量公開徵集若需嚴格個人配額、CAPTCHA 或上傳頻率控制，應在開放前增加受驗證的上傳閘道，不依賴副檔名檢查防濫用。

## 尚未實作的管理功能

無研究團隊 Web 管理後台、憑證簽章、伺服器檔案雜湊、掃毒自動化、定時撤回清理、模型訓練或原文輸出防護。這些不能以目前網站存在就推定已完成；目前需人工審核與維運執行。
